# 阶段执行与交接约定

启动阶段时读取本文件。它定义跨阶段执行规则；阶段参考文件描述具体任务。其他文件中的固定确认次数、全链路回溯和逐文件日志要求统一按本约定执行。当前用户指令和项目权限优先，已确认的授权持续有效；旧文档与当前指令冲突时以当前指令为准。缺失的 `docs/user_requirements.md` 不构成阻塞，只记录已确认的约束，不把模型推断记成用户要求。

## 确认与执行

- 在已授权范围内连续完成阅读、检索、局部修复、文档同步和轻量验证；先检查已有上下文，不重复询问已回答事项。
- 研究方向、核心假设、方法或评估协议发生实质改变时，汇总证据和影响，集中确认一次。大纲获批后可以展开正文，无需再逐节确认。
- 昂贵实验、付费资源及外部发布只在授权范围内执行；缺少必要授权时询问具体动作。用户已授权连续完成多个阶段时可以继续，否则阶段末提供下一步命令。
- 普通实现错误直接修复并验证；方法变化才同步受影响的设计文档。不因修复一个路径或 import 错误重走 B/C/D。未解决的真正阻塞说明证据、已尝试的方法和所缺信息。

## 阶段状态

除纯只读请求外，在完成一个有意义的工作单元后维护 `docs/research_state.json`。不为每个文件保存一次状态；写入必须遵守用户的目录权限。示例：

```json
{
  "schema_version": 1,
  "active_phase": "C",
  "phases": {
    "C": {
      "status": "in_progress",
      "artifacts": [{"path": "docs/idea_report.md", "sha256": "<实际文件哈希>"}],
      "completion_evidence": [],
      "confirmation": {"status": "not_requested", "scope": "", "source": ""},
      "updated_at": "<带时区的 ISO 8601 时间>"
    }
  }
}
```

- 阶段编号使用 A–F、G.0–G.8（英文版无 G.8）。`status` 取 `not_started`、`in_progress`、`complete`、`needs_revalidation` 或 `blocked`。
- 产物记录项目相对路径及实际 SHA-256；不得把示例占位值写成真实记录。完成依据记录具体检查及结果，例如“Part 3 已有假设、对照、评估与资源方案”，而不是“文件存在”。
- `confirmation.status` 为 `not_requested`、`confirmed` 或 `not_required`。确认范围和来源记录实际用户指令；`not_required` 需说明属于哪项已有授权或常规工作。不要编造确认或时间。
- `complete` 要求内容实质完成、必要检查通过、需要的确认已获得。只完成实现、尚未运行时，明确记录验证范围，不声称完整训练已通过。
- 产物哈希变化或上游方法/评估变化后，检查受影响的下游阶段；仅使相关结论失效，不机械作废全部阶段。审阅报告须绑定手稿、评估结果和引用文件的版本；稿件或证据改变后需重新审阅相关 claim。
- 状态缺失、损坏、版本不支持或与产物冲突时，保留原文件，按内容只读恢复候选状态并说明不确定性；状态损坏或关键状态有歧义时，确认后再修复；在已授权的阶段工作中可直接初始化缺失状态，只记录已知事实。无状态文件的旧项目仍可直接使用各阶段技能。

## 科研与复现

实验检验可证伪的假设。预先列出支持、反对和无法区分假设的结果，保留失败与负结果；不把“胜过全部 baseline”作为成立条件。不反复使用测试集选模型或调参；记录数据划分、预处理拟合范围、种子、搜索预算和指标实现。

在规划时了解可用设备、时间与预算。分别列出完整证据方案和可执行的核心方案，说明缩减后的结论边界。文献与实验数量是按问题调整的参考，停止于证据覆盖充分，不为凑数量重复阅读或实验。

复用项目现有环境管理方式并服从用户要求。若要求 uv，使用工作目录内的环境、解释器与缓存，按项目规则维护 `pyproject.toml`、`uv.lock` 和 `.python-version`。记录 Python、PyTorch、CUDA 和其他依赖版本；硬件专用包可单独安装，但必须记录版本、索引及重建命令。不得用无版本的依赖清单作为唯一复现依据。

历史事件日志只追加，已有结论通过新的纠正条目修订。进度表、当前运行说明和已知问题是可更新的摘要；按有意义的改动单元记一次日志，标明涉及文件与验证结果。
